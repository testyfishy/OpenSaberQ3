# v0.3 report — what changed, what was measured

Written for the person who has to decide what to ship, not for a changelog. Every claim below
has a number attached, and every number came off the headset with the same harness.

## 1. Performance

### The stutter you were feeling was a bug, and it is fixed

Three minutes of play, same map, before and after one line of code:

| | on time | dropped | p99 | mean frame, thirds |
|---|---|---|---|---|
| before | 64.3% | 0.72% | 11.98 ms | 8.40 / 8.69 / 8.95 ms |
| after | **78.3%** | **0.21%** | **10.37 ms** | **8.34 / 8.35 / 8.38 ms** |

The decay is what you described as "worse the longer I play": the frame time used to climb
0.55 ms over three minutes, tracking how many notes were live. Cause: `Cuttable._physics_process`
read `global_transform` twice per tick per live note, immediately after writing the same value
locally. Notes hang off an unrotated track at the origin, so that was two thousand pointless
transform walks a second.

### The limiter is the GPU, and we were wrong about the CPU

The runtime's own counters during play: **GPU 86% of the frame budget, CPU 22%.** Everything in
the optimisation plan had been aimed at the CPU. Dropping the physics rate to 60 Hz changed the
result by 0.6 points; dropping the render target changed it by six times that.

### The GPU curve, measured per lever

| configuration | GPU% | on time | dropped | p99 |
|---|---|---|---|---|
| Quality — 2107×2208, 4× MSAA | 0.86 | 78.3% | 0.21% | 10.37 |
| MSAA 2× only | 0.77 | 82.4% | 0.02% | 9.57 |
| FFR 2 only | 0.80 | 85.1% | 0.07% | 9.59 |
| Balanced — 1848×1936, 4× MSAA, FFR 1 | 0.75 | 84.7% | 0.00% | 9.64 |
| Render 1.0 only — 1680×1760 | 0.69 | 88.6% | 0.00% | 9.52 |
| **Performance — 1680×1760, 2× MSAA, FFR 2** | **0.64–0.67** | **84–91%** | **0.00–0.01%** | **9.5–9.8** |

Shipped default is **Performance**. Verified on a device with an older config, so the one-time
migration ran: `render_scale 1.0`, `msaa 2×`, `foveation 2`, render target 1680×1760.

**Dropped frames fell 20×** (0.21% → 0.01%, one frame in 6,950). That is the number a player
feels as a hitch.

### What is not achievable, stated plainly

"Every frame under 8.33 ms" is not reachable on this device. The empty-scene floor — nothing
spawning, 33% GPU free — still puts ~11% of frames in the 8.75–9.8 ms band. That is compositor
pacing jitter, not workload. The honest target, and the one we now meet, is: **120 fps, zero
dropped frames, ~3 ms of GPU slack, no decay over a session.**

### Shipped default, 40 s capture — the 180 s confirmation is still pending

| | before (v0.3 start) | shipped default |
|---|---|---|
| on time | 64.3% | **87.1%** |
| dropped | 0.72% | **0.00%** (none in 4,551 frames) |
| p99 | 11.98 ms | **9.28 ms** |
| mean frame, thirds | 8.40 / 8.69 / 8.95 | **8.34 / 8.33 / 8.33 ms** |
| on-time, thirds | 78.5 / 62.6 / 51.7% | **89.6 / 84.9 / 86.9%** |

The drift is gone in this window: the mean no longer rises and the thirds hold within 5 points
instead of collapsing by 27.

**Caveat, recorded deliberately:** this capture is 40 s, not the 180 s it was meant to be. The
flag asked for 180 and the harness reported `limit_s=40.000` with 4,791 samples. A 40 s window
cannot prove the absence of a slow drift — that is exactly what a 180 s run is for. The earlier
180 s arms did hold flat, but they were the pre-preset build. Re-running with an explicit
`max_duration` and checking the sample count before quoting it.

### Method, because it was wrong twice

- 60 s comparisons have a ±4 point spread; three runs of one scenario measured 74.5 / 78.4 /
  78.3. Two "findings" were withdrawn after re-measurement.
- A long claim needs a long capture, and the capture length must be verified: one run labelled
  180 s turned out to be 40 s because the harness clamped the duration.
- Report thirds, not averages: a run averaging 78% while decaying to 52% is worse for a player
  than one holding 74% flat.

## 2. Audio

The old samples were the mechanical cause of "tinny and quiet":

| | peak | RMS | crest | <80 Hz | 80–300 Hz | 1–4 kHz |
|---|---|---|---|---|---|---|
| hard_01 before | −3.1 dB | **−19.6 dB** | 16.5 dB | 0.0% | 0.0% | 20.8% |
| hard_01 after | −0.9 dB | **−9.0 dB** | 8.1 dB | 14.0% | 33.2% | 0.9% |

Every hit is now one layered impact (sub with a falling pitch, body, crack, air) with the crest
compressed instead of peak-normalised: **+8 to +9 dB RMS**, and low-mid energy that was entirely
absent. The "accent" layer used to be 98.6% treble, so swinging faster made hits thinner; it is
now extra low-mid weight.

`tools/audio/analyse_hitsounds.py` prints that table for any build.

Known limits, from the platform: Quest 3 speakers roll off below ~150–200 Hz, and Godot has no
HRTF, so left/right is achievable by panning but above/below is not.

## 3. Haptics

One 100 ms pulse at 0.75 for every event — a clean cut, a wrong-colour cut and a bomb — replaced
with per-event patterns:

- cut: 28 ms, amplitude from speed and angle accuracy
- fast clean cut: plus a 12 ms tick at +30 ms
- wrong colour / bomb: 45 ms at 0.28

Godot exposes only amplitude and duration on the simple haptic path, so the pattern is built
from duration and delay rather than a waveform.

## 4. Presentation

**Sky:** black void is now the default, with Gradient and Panorama as options. The trap was
handled — the sky used to supply ambient and reflected light, so void sets ambient explicitly
rather than leaving the scene dark. Void is also the cheapest of the three to draw.

**BeatSaver scrolling:** the list moved but the UI canvas only repaints on input, so it appeared
to jump and then stop; the speed curve also started at 10 px/s, which rounded to zero at 120 Hz.
Both fixed. Probe: **118 of 120 frames move the list**, steps ramping 1→10 px.

## 5. Debugging instruments added

- `[bench] player_capture=true` — records **your** play to the same CSV as a bot run, so stutter
  can be measured against the map that actually gave you trouble.
- `[bench] ui_scroll_probe=true` — turns "notchy" into a per-frame number.
- `[bench] no_notes / hud_off / physics_hz / floor_off / no_audio` — delete one subsystem at a
  time so a cost can be attributed instead of guessed.
- `tools/audio/analyse_hitsounds.py` — level, crest and five band percentages per sample.
